Event-Driven Architectures inverts dependencies (like dependency injection!) when compared to request-response systems.

- What is an event?
  - An **immutable** fact that happened in the past that cannot be changed.
- What is an event-driven architecture?
  - A **communication pattern**, and a way of modelling the integration between systems.
- Event-based system
  - Reacts to system events like btn_Click or s3-file-uploaded
- Event-driven system
  - Reacts to business events like OrderCreated or TaxReturnUploaded

- Messages
  - Events
    - Notification Event (thin event that just carries ids)
      - Often results in calls back into the publishing service, which can bog down the publisher
    - Event Carried State Transfer (thick event)
      - Increases coupling because more properties exposed
  - Commands
  - Queries

Message Channel

- Point to Point
- Publish / Subscribe

Channel Types

- Queue
  - Durable messages (SQS, Queue type in RabbitMQ, Azure SB Queues)
  - No guarantee ordering generally
- Bus / Topic
  - Pub/sub channels, most channels in EDA
  - Generally not durable if subscriber is offline
- Stream
  - Kafka, Amz Kinesis, Az Event Hub
  - Pub/sub + durability
  - Offset-based, append-only, immutable, partitioned log

Observability is a challenge, there will be solutions later.

## Build a Simple Producer

Again, the upfront question before the module starts:

- What does it mean to be a good producer? What do you need to think about?
  - Maintain an event schema
    - Well-named events
    - Identify source
    - Align to Cloud Events, probably
  - Make only forward compatible changes as existing consumers will still be deployed when newer versions of the producer are deployed
    - Yes the naming of backward vs forward compatible schemas is confusing

Outbox pattern
- Use when you need state saved and event publishing to be transactional
- Usual implentation is an Outbox table in the same DB as your state
  - INSERT to all state tables AND the outbox table in the same transaction
  - Return success to the user
  - Background worker comes along later and picks up messages from the outbox table
  - Publishes to the message bus (RabbitMQ etc)
  - UPDATE or DELETE from the outbox table to mark the message as processed

## Build a Simple Consumer

Consumer responsibilities
- Plan for ingestion rate
  - Maybe introduce a queue/inbox for yourself
- Plan for failure
  - Retries are great, but not forever
  - Dead letter queue to handle Poison pill message
  - Be sure to manage your DLQ
- Plan for idempotency
  - May well get the same message more than once
  - Check incoming IDs to see if you've already processed it

## EDA in Practice

Most important things as EDA systems get more complex? My current guess:
- Observability
- e2e Testing
- Performance Testing

Notifying the user
- Polling
- Web Sockets / Server-Sent Events / Long polling (SignalR)

Versioning
- Create new version of an event
- Mark the older event as deprecated
- Publish both versions for a while
- Deprecate the older event as a predetermined and well know date
  - Don't want to keep maintaining infinite versions

Application Failures
- Durable storage of messages lets processes pick up where they left off
- Process can get stuck with Choreography if one service is offline or erroring
- Orchestration may be the fix
